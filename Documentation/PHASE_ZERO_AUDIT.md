## 1. القرار التقني المعتمد

- التطبيق النشط: Next.js + React + Phaser 3 داخل `web/`.
- Phaser مسؤول عن حلقة اللعب الفعلية، المشاهد، التصادم، الأنيميشن، والحركة.
- Next.js مسؤول عن واجهات التطبيق وStudio وواجهات API.
- مشروع Godot محفوظ كمرجع متوقف مؤقتًا، ولا يُنقل إليه التطوير النشط.
- توجد أيضًا ملفات ومجلدات Unity تاريخية في المستودع؛ لا تُعامل على أنها المسار النشط.
- تجربة المطور المستهدفة: Windows + Chrome محليًا. التغليف إلى Android مؤجل حتى استقرار نسخة المتصفح.

## 6. نتائج فحص Studio على فرع الميزة

### ما هو موجود

- تسجيل دخول مسؤول وجلسة Cookie موقعة.
- سجل أصول على فرع `studio/assets`.
- رفع أصول إلى GitHub storage.
- واجهة نباتات تتضمن اختيار السلوك وبعض خصائص القتال.
- سلوكيات نبات مدعومة: projectile وmelee وcontact وblocker وenergy.
- تحرير بيانات الأصل دون إعادة رفع الصورة في بعض الحالات.
- تجهيز النبات للاختبار، ثم نشره بعد الاختبار.
- اختبار مباشر لكتالوج النباتات من خلال جلسة Studio.

### الفجوات المؤكدة

1. واجهة Studio الحالية ليست محررًا عامًا لكل أنواع المحتوى؛ تحرير خصائص القتال مخصص للنباتات.
2. لا توجد دورة حياة عامة مكتملة للوحوش والمقذوفات والمؤثرات والعناصر والصوتيات.
3. لا يوجد محرر خرائط بصري.
4. لا يوجد منشئ مراحل وموجات بصري متكامل.
5. لا يوجد نظام عام لإدارة الاقتصاد والتقدم والمهام من Studio.
6. API الحالية تدعم `GET` و`POST` و`PATCH`، ولا تظهر عملية `DELETE` عامة.
7. عمليات PATCH الحالية تركز على `prepare-test` و`publish`؛ لا يوجد نظام عام موحد للتعطيل والأرشفة والاسترجاع.
8. لا يوجد سجل إصدارات عام مع مقارنة واستعادة لأي نوع محتوى.
9. GitHub Contents API تنفذ عمليات حفظ متعددة على شكل commits منفصلة؛ ليست معاملة ذرية واحدة. يجب تصميم نشر أكثر أمانًا قبل توسيع النشر إلى حزم محتوى مترابطة.
10. التحقق من نوع الملف والحجم وبعض إعدادات الشبكة موجود، لكن فحص أبعاد الصور والإطارات والمعاينة البصرية ليست دورة كاملة بعد.
11. يوجد في `web/package.json` على فرع #52 أمر `studio:sync`، بينما توثيق دورة الاختبار يصف الاختبار المباشر دون مزامنة. يجب حسم هذا التعارض وإزالة أي اعتماد يومي على أوامر Terminal من تجربة المستخدم.
12. يجب أن تظل بيانات المسودة منفصلة عن الإصدار المنشور، وألا يؤدي فشل عملية جزئية إلى كتالوج يشير إلى ملفات ناقصة.

## 9.1 مراجعة ساكنة إضافية لطلبات الدمج بتاريخ 2026-11-21

أُعيد فحص PR #51 و#52 وبيانات CI، وقُرئت واجهات API وصفحة Studio وملفات تعريف سلوك النباتات وأجزاء ربط Phaser.

### نتائج مؤكدة

1. آخر تشغيل ظاهر لـ `Web quality gate` على PR #51 (run `44772710575`) وPR #52 (run `44831531658`) انتهى بـ `failure`. أُعيدت محاولة الوظائف الفاشلة؛ فشل التشغيلان مجددًا (PR #52 في run `44836989008`). استجابة الوظائف لا تعرض خطوات تنفيذ (`steps = null/[]`) وسجل الوظيفة غير متاح؛ لذلك لا نعرف سبب فشل التشغيل ولا يوجد دليل أن lint أو tests أو build قد نُفذت. كما لم يظهر تشغيل جديد منفصل يثبت فحص commit إصلاح POST.
2. أثناء مراجعة `web/app/api/studio/assets/route.js` في فرع #52، وُجد أن كتلة `try` داخل POST لا تحتوي `catch` أو `finally` قبل نهاية المعالج؛ وهذا يجعل الملف غير صالح للتحليل النحوي. أُضيفت معالجة خطأ في commit `559ddc925d4abebfdae934830649647064eeff93` على فرع #52. يجب أن يؤكد Node/Build محليًا زوال العائق؛ لم يُنفذ تحقق محلي بعد.
3. نشر النبات في #52 يكتب ملفات النبات والمقذوف والكتالوج إلى `main` عبر طلبات GitHub Contents متتابعة ومنفصلة. هذا ليس نشرًا ذريًا: فشل خطوة لاحقة قد يترك ملفًا أو كتالوجًا منشورًا جزئيًا. كما أن تحديث سجل المسودات منفصل عن تحديث الكتالوج.
4. لا يظهر في مسار الحفظ قفل أو تحقق optimistic concurrency على نسخة سجل الأصول؛ عمليتا حفظ متزامنتان قد تقرآن السجل نفسه ثم تكتبان نسختين متعارضتين، وقد تفقد إحداهما تغييرات الأخرى.
5. زر «نشر» في Studio يكتب مباشرة إلى `main`، وليس عبر Release Preview أو PR قابل للمراجعة. هذا يتجاوز بوابة موافقة الدمج/النشر المعتمدة للمشروع؛ يجب تعطيل هذا المسار أو تحويله إلى طلب إصدار ومراجعة صريحة قبل أي كتابة إلى `main`.
6. اختبارات `studio-plant-workflow.test.mjs` تعتمد في مواضع أساسية على مطابقة نصوص/Regex في الملفات، وتثبت وجود مسارات الكود لا نجاح طلبات API أو سلوك Phaser في تشغيل حقيقي. يلزم إضافة اختبارات سلوكية لمسارات الرفع والتعديل والتحضير للاختبار والنشر والفشل الجزئي، ثم اختبار متصفح/لعبة.
7. تكامل Phaser يقرأ كتالوج المسودات المختبرة ويهيئ سلوكيات projectile وmelee وcontact وblocker وenergy في المشهد. هذا دليل على وجود ربط مصدري، لكنه لا يثبت بعد أن جميع القيم والسلوكيات صحيحة بصريًا أو متوازنة أثناء اللعب.

### إجراء التصحيح

- أُصلح نقص `catch` في POST على فرع #52 فقط، ولم يُدمج أي PR إلى `main`.
- تبقى مخاطر النشر المباشر والتزامن والنشر الجزئي مفتوحة، ويجب حلها قبل اعتماد Workflow النشر.

## 9.3 مراجعة أمن الجلسة والتزامن ونتيجة إعادة CI — 2026-11-21

أُعيدت قراءة الملفات الفعلية عند رأس PR #52 الحالي `559ddc925d4abebfdae934830649647064eeff93`، بما فيها `web/app/api/studio/session/route.js` و`web/app/api/studio/assets/route.js` وواجهة Studio ومحرك المعركة واختبارات دورة النبات.

### نتائج مؤكدة

1. المصادقة في #52 لم تعد تعتمد على إرسال رمز المسؤول في كل طلب كما كان في أساس #51. مسار الجلسة ينشئ nonce عشوائيًا بطول 32 بايت ويوقّعه بـ HMAC-SHA256، ثم يضع Cookie باسم `fvm_studio_session` بخصائص `HttpOnly` و`SameSite=Strict` و`Path=/api/studio` ومدة 12 ساعة، مع `Secure` في الإنتاج. دالة التفويض في API الأصول تتحقق من التوقيع بمقارنة ثابتة الزمن. هذا تحسن مؤكد مقارنة بالأساس الأول.
2. مسار `DELETE /api/studio/session` لا يشترط جلسة صالحة قبل مسح Cookie؛ الأثر الظاهر هو تسجيل خروج المتصفح الذي استقبل الاستجابة، وليس منح صلاحية أو تعديل بيانات. لا يُعد ذلك تجاوزًا للمصادقة، لكنه يسمح بطلب تسجيل خروج غير مرغوب من المتصفح إذا أمكن استدعاء المسار.
3. أُعيد تشغيل Job الفاشل في run `44836989008` على رأس #52. انتهى مجددًا بـ `failure`، والـ Job يعرض `steps = null` ولا يتوفر سجل؛ محاولة تنزيل السجل أعادت 404 من مخزن السجلات. لم تُنفذ خطوات قابلة للفحص، لذلك لا يمكن تشخيص فشل الكود ولا إثبات نجاح الاختبارات أو lint أو build.
4. القيمة الحالية في `BattleScene.js` هي `PLAYTEST_ALL_PLANTS = false`، خلافًا للقيمة التي ظهرت في قراءة أقدم. المشهد ما يزال يضيف نباتات Studio بحالة testing إلى التشكيلة الاختبارية تلقائيًا مع حصر التشكيلة في سبعة. هذا لا يثبت نجاح دورة اللعب، لكنه يصحح نتيجة التدقيق السابقة.
5. اختبار `studio-plant-workflow.test.mjs` يفحص أجزاء كبيرة من الربط باستخدام مطابقة النصوص وRegex. وهو مفيد كفحص وجود/بنية، لكنه لا يحاكي جلسة Cookie أو GitHub API ولا يثبت أن Phaser حمّل Bamboo وأطلق المقذوف وأصاب الهدف.
6. تأكدت فجوة التزامن في كتابة السجل: مسار POST يقرأ Registry ويكوّن `next` من تلك النسخة، ثم `githubPut` يجلب SHA الحالي لحظة الكتابة ويستخدمه دون مقارنة مع نسخة Registry التي بُني عليها `next`. إذا قرأ طلبان النسخة القديمة نفسها، ثم كتب الثاني بعد الأول، يستطيع الثاني جلب SHA الجديد وكتابة snapshot قديم فوقه؛ وهذا قد يفقد تسجيل الأصل الأول أو تعديلاته. ينطبق نمط read-modify-write أيضًا على تحديث كتالوج النشر. يلزم optimistic concurrency باستخدام SHA الذي تمت قراءته في بداية العملية، مع إرجاع تعارض واضح وإعادة تحميل البيانات بدل الكتابة فوق تحديث أحدث.
7. بقي نشر الإصدار إلى `main` سلسلة commits منفصلة، ولا يزال زر Studio يكتب إلى فرع اللعبة مباشرة دون Release PR/موافقة. لذلك يبقى خطر النشر الجزئي وتجاوز مراجعة الإصدار قائمًا كما ورد في 9.1.
