# الخطة الحاكمة وسجل القرارات — FarmVsMonsters

> هذه الوثيقة هي نقطة الدخول الرئيسية لتخطيط المشروع. تُراجع وتُحدّث قبل بدء كل مرحلة، وتُسجل فيها القرارات والتعديلات المعتمدة. وجود الخطة هنا لا يعني أن جميع الأنظمة منفذة.

**الحالة:** مسودة عمل معتمدة للمراجعة والتطوير قبل متابعة التنفيذ.  
**المرحلة الحالية:** المرحلة 0 — التدقيق وتثبيت الأساس.  
**قاعدة التوقف:** لا يبدأ تنفيذ المرحلة 1 أو أي مرحلة لاحقة قبل إغلاق بوابة المرحلة 0 واعتماد الخطة المحدثة.

## 1. الرؤية

بناء FarmVsMonsters كلعبة قابلة للتوسع، وإدارة اللعبة ومحتواها وتشغيلها من خلال Studio واحد واضح وسهل. الهدف ليس مجرد لوحة إعدادات، بل أداة إنشاء وإدارة واختبار ونشر حقيقية متصلة بمحرك اللعبة وبياناتها.

## 2. المبادئ الثلاثة الملزمة

1. **الإدارة الشاملة:** أي شيء يمكن للاعب رؤيته أو استخدامه أو التأثر به داخل اللعبة يجب أن تكون له إدارة واضحة في Studio، مع اتصال حقيقي بمحرك اللعبة وبياناتها.
2. **الإنشاء والتطوير:** Studio يجب أن ينشئ محتوى جديدًا ويعدله ويديره، لا أن يقتصر على تغيير إعدادات عناصر ثابتة.
3. **سهولة الاستخدام والتحكم:** يجب أن تكون الإضافة والتعديل والاختبار والنشر والحذف والإيقاف والاسترجاع لكل جزء من اللعبة سهلة من واجهة Studio، دون حاجة المستخدم إلى تعديل الكود أو الملفات أو استخدام Terminal في العمل اليومي.

هذه المبادئ شروط قبول لكل ميزة وليست شعارات تصميمية.

## 3. تعريف اكتمال أي ميزة

لا تُعد الميزة مكتملة إلا إذا تحقق المسار التالي بحسب طبيعتها:

`Studio UI → API → Service → Validation → Registry/Storage → Runtime → Game Engine → Test → Publish`

ويجب أن تتوفر، حيث تنطبق:
- إنشاء عنصر جديد ونسخه وتعديله.
- حفظ مسودة ومعاينة التغييرات.
- اختبار العنصر منفردًا وضمن سياقه الحقيقي.
- فحص العلاقات والتبعيات قبل النشر أو الحذف.
- نشر إصدار واضح دون تغيير إصدار اللاعبين أثناء التحرير.
- تعطيل أو أرشفة آمنة، واسترجاع عند الحاجة.
- سجل يوضح من غيّر ماذا ومتى، مع مقارنة الإصدارات.
- رسائل خطأ مفهومة وإجراءات إصلاح واضحة.

كل زر يجب أن ينفذ عملية فعلية. الواجهة غير المرتبطة بالبيانات والمحرك لا تحقق الميثاق.

## 5. قواعد تجربة المستخدم داخل Studio

- واجهة واضحة وبسيطة، عربية عند الحاجة، وتقلل الخطوات غير الضرورية.
- البحث والفلاتر والمعاينة والنسخ من العناصر الموجودة.
- إنشاء المحتوى من الصفر دون الحاجة إلى تجهيز ملفات أو تعديل كود يدويًا.
- حفظ مسودة وحماية من فقد التعديلات.
- عرض التبعيات والتحذيرات قبل عمليات النشر والحذف.
- حذف آمن أو أرشفة بدل الحذف النهائي متى كان ذلك مناسبًا.
- اختبار قبل النشر، مع إظهار نتيجة الاختبار.
- نشر إصدار محدد وإمكانية الرجوع إلى إصدار سابق.
- لا يحتاج المستخدم إلى Terminal أو تحرير ملفات للمهمات التشغيلية اليومية.

## 6. قواعد هندسية وتشغيلية

- Phaser/Next.js داخل `web/` هو مسار التطبيق النشط بحسب التدقيق الحالي؛ لا تُنقل المسؤوليات إلى مشاريع Godot أو Unity التاريخية دون قرار جديد.
- بيانات المحتوى القابلة للتغيير تُنظم في Registry/Storage بمعرفات ثابتة وعلاقات صريحة.
- منطق المحرك العام يبقى في الكود؛ أما خصائص كل نبات أو وحش أو مقذوف أو مرحلة فتكون بيانات قابلة للتحرير متى أمكن.
- لا نكرر مصدر القيمة الواحدة ولا نربط العلاقات بأسماء الملفات.
- لا نعيد كتابة الأنظمة الكبيرة دفعة واحدة؛ نفككها تدريجيًا مع الحفاظ على السلوك المعتمد.
- النشر متعدد الملفات يجب أن يكون متماسكًا وقابلًا للتعافي؛ لا نسمح بكتالوج يشير إلى أصول ناقصة.
- لا نغير الأصول أو الأنيميشنات المعتمدة دون طلب أو سبب مثبت.
- لا نضيف خدمات مدفوعة دون موافقة مسبقة.
- لا ندمج إلى `main` دون موافقة صريحة.
- لا نصف اختبارًا بأنه ناجح ما لم يُنفذ وتُسجل نتيجته.
- لا نعتبر وجود صفحة أو API أو ملف Registry وحده دليلًا على اكتمال التكامل.

## 7. الحالة التنفيذية الحالية

### المرحلة 0 — قيد الإنجاز

ما تم توثيقه في التدقيق الحالي:
- مراجعة بنية المستودع وتحديد تطبيق Next.js/Phaser داخل `web/` بوصفه المسار النشط.
- مراجعة الفروع وطلبات الدمج #51 و#52 و#53.
- تحديد أن #51 و#52 ما زالا أساسًا قيد المراجعة، ولم يتم دمجهما.
- توثيق الفجوات الحالية في Studio، مصادر البيانات، إدارة المحتوى، النشر والإصدارات.
- توثيق حدود نتائج CI التي لم تخصص Runner ولم تنفذ خطوات اختبار.

ما لا يزال مطلوبًا قبل إغلاق المرحلة:
1. تحقق فعلي من اختبارات Node وESLint وProduction Build في بيئة مناسبة، أو Runner ينفذ الخطوات.
2. فتح اللعبة في Chrome والتحقق من مسارات اللعب وتحميل الأصول.
3. التحقق داخل المعركة من سلوك Bamboo Throwing؛ قيمة المدى المسجلة وحدها لا تثبت حل المشكلة.
4. استكمال مصفوفة مصادر البيانات والتبعيات End-to-End.
5. تسجيل النتائج الفعلية والعيوب وخطوات إعادة إنتاجها.
6. اعتماد نقطة أساس وخطة المرحلة 1 بعد مراجعة هذه الوثائق.

**لا تعتبر المرحلة 0 مكتملة حاليًا. ولا تبدأ المرحلة 1 قبل إغلاق هذه القائمة أو توثيق سبب مقبول لكل بند واعتماد المستخدم لذلك.**

## 8. طريقة تعديل الخطة واعتمادها

هذه خطة حية قابلة للمراجعة وليست قيدًا يمنع التحسين:
1. قبل بدء مرحلة جديدة، نراجع نطاقها ومعيار قبولها والتبعيات والمخاطر.
2. يمكن للمستخدم طلب إضافة أو حذف أو إعادة ترتيب أي نظام أو مرحلة.
3. تُسجل التغييرات المقترحة منفصلة عن القرارات المعتمدة حتى يوافق المستخدم عليها.
4. عند اعتماد تعديل، تُحدّث هذه الوثيقة والوثائق التفصيلية المرتبطة بها في نفس فرع التوثيق.
5. لا يُغيّر ترتيب التنفيذ أو بوابات القبول ضمنيًا.
6. لا نتابع التنفيذ لمجرد أن الخطة مكتوبة؛ ننتظر مراجعة المستخدم واعتماده للنسخة التي يريدها.
