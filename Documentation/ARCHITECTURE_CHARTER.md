# الميثاق المعماري الحاكم — FarmVsMonsters وStudio

**الحالة:** ميثاق معتمد وملزم لكل أعمال التصميم والتطوير.  
**النطاق:** لعبة FarmVsMonsters، محركها، Studio، بياناتها، أدوات الأصول، الاختبار والنشر والتشغيل.

## 1. الغاية

بناء لعبة قابلة للتوسع، مع Studio يكون مركز التحكم العملي بها. يجب أن يستطيع مالك اللعبة إنشاء وتعديل واختبار ونشر وإيقاف واسترجاع كل محتوى اللعبة من واجهات واضحة، دون الحاجة إلى كتابة الكود أو تعديل الملفات أو تشغيل أوامر Terminal في العمليات اليومية.

لا نبني لوحة تحكم تجميلية حول اللعبة؛ نبني منظومة يكون فيها Studio متصلًا فعليًا ببيانات اللعبة ومحركها.

## 2. المبادئ الثلاثة غير القابلة للتفاوض

### المبدأ الأول — الإدارة الشاملة

أي شيء يمكن للاعب رؤيته أو استخدامه أو التأثر به داخل FarmVsMonsters يجب أن تكون له إدارة واضحة في Studio، مع اتصال حقيقي بمحرك اللعبة وبياناتها.

### المبدأ الثاني — الإنشاء والتطوير وليس الإعداد فقط

لا يكون Studio مجرد لوحة إعدادات؛ يجب أن يستطيع إنشاء محتوى جديد وتعديله وإدارته، وليس فقط تغيير قيم عناصر ثابتة موجودة مسبقًا.

### المبدأ الثالث — سهولة الاستخدام والتحكم

يجب أن تكون جميع عمليات الإضافة والتعديل والاختبار والنشر والحذف والإيقاف والاسترجاع لكل جزء من اللعبة ممكنة عبر واجهة واضحة وبسيطة في Studio، دون التعامل اليدوي مع الكود أو Terminal أو الملفات.

## 3. نطاق الإدارة الإلزامي

يجب أن تتوفر إدارة مناسبة لكل من:
- النباتات ومستوياتها وخصائصها وسلوكها.
- الوحوش وفئاتها وقدراتها ومراحل الزعماء.
- المقذوفات والأسلحة والتأثيرات المرتبطة بها.
- الصور وSprite Sheets والأنيميشنات والصوتيات والمؤثرات.
- الخرائط والعوالم والخلايا والعوائق ومسارات الحركة.
- المراحل والموجات وتوقيت الظهور وشروط الفوز والخسارة.
- الطاقة والعملات والأسعار والتكاليف والمكافآت والاقتصاد.
- مخزون اللاعب والتقدم والفتح والترقيات والمهام والإنجازات.
- إعدادات الصعوبة والتوازن وقواعد اللعب.
- واجهات اللاعب والنصوص والإعدادات والعناصر التفاعلية.
- إصدارات اللعبة والتحليلات وسجلات الأخطاء.

## 4. فصل المسؤوليات

### Studio
واجهة المستخدم لإدارة المحتوى والخصائص والعمليات. لا تتصل مباشرة بملفات التخزين ولا تعدل كائنات المحرك الحية بطرق عشوائية.

### API والخدمات
تتحقق من الهوية والصلاحيات والبيانات والعلاقات، وتنفذ عمليات الإنشاء والتعديل والنسخ والاختبار والنشر والأرشفة والاسترجاع.

### Content Registry / Storage
المصدر المنظم للمحتوى، بمعرفات ثابتة وإصدارات وعلاقات واضحة. يبدأ باستخدام البنية الموجودة عند الحاجة، لكن يجب أن يدعم طبقة تخزين قابلة للتبديل دون ربط واجهة Studio بمزود واحد.

### Game Runtime
يقرأ المحتوى المعتمد ويحوّله إلى كيانات تشغيلية. لا يعتمد على أسماء ملفات عشوائية أو قيم مخفية مكررة داخل الواجهات.

### Engine Code
يحتوي على القواعد العامة والخوارزميات: الحركة، الاستهداف، التصادم، الضرر، المقذوفات، الموجات، والمحاكاة. أما القيم التي تختلف بين عنصر وآخر فتكون بيانات قابلة للتحرير.

## 5. قاعدة End-to-End

لا تعتبر أي ميزة مكتملة إلا عندما يعمل المسار كاملًا:

`Studio UI → API → Service → Validation → Registry/Storage → Runtime Adapter → Game Engine → Test → Publish`

يجب أن يكون لكل زر عملية حقيقية، ولكل حقل تأثير موثق على بيانات اللعبة أو سلوكها. لا تُقبل واجهات شكلية أو بيانات تجريبية غير متصلة.

## 6. المعرفات والعلاقات

- لكل عنصر معرف ثابت لا يتغير عند إعادة التسمية.
- تُربط العناصر بالمعرفات لا بأسماء الملفات.
- تُعرّف العلاقات صراحةً: نبات ← مقذوف، مرحلة ← خريطة، مرحلة ← موجات، موجة ← تشكيل وحوش، عنصر ← أنيميشن/صوت.
- يمنع الحذف أو التعطيل من كسر عنصر يعتمد عليه دون تحذير ومعالجة.
- يجب فحص التبعيات قبل النشر والحذف.

## 7. دورة حياة المحتوى

الحالات القياسية:
- Draft: مسودة.
- Testing: قيد الاختبار.
- Approved: معتمد.
- Published: منشور.
- Disabled: متوقف مؤقتًا مع الاحتفاظ بالبيانات.
- Archived: مؤرشف وغير مستخدم.

التعديل على عنصر منشور ينشئ مسودة/إصدارًا جديدًا؛ لا يغيّر الإصدار الذي يلعب به المستخدمون. لا ينتقل المحتوى إلى Production إلا بعد التحقق والاعتماد.

## 8. الإصدارات والاسترجاع

- كل إصدار منشور غير قابل للتغيير.
- تحفظ مقارنة بين الإصدارات وتفاصيل من قام بالتعديل ومتى.
- يجب استرجاع إصدار سابق دون إعادة بناء المحتوى يدويًا.
- يجب أن تكون عملية النشر قابلة للتأكد من اكتمالها.
- لا يجوز أن تشير Manifest أو Catalog منشور إلى ملف لم يتم نشره.
- العمليات متعددة الملفات يجب أن تستخدم آلية نشر ذرية أو حزمة إصدار ذات مؤشر تفعيل؛ لا تعتمد على سلسلة commits جزئية دون تعافٍ.

## 9. سهولة الاستخدام

- واجهات عربية واضحة ومصطلحات مفهومة.
- بحث وفلاتر ومعاينة قبل الحفظ.
- إدخال رقمي دقيق مع حدود وقيم افتراضية موثقة.
- نسخ عنصر لإنشاء عنصر جديد دون تعديل الأصل.
- حفظ مسودة تلقائي أو حماية من فقد التعديلات.
- تأكيد واضح للعمليات الخطرة.
- عرض سبب فشل العملية وكيفية إصلاحه.
- عمليات جماعية آمنة عند الحاجة.
- لا يطلب من المستخدم فتح ملفات المشروع أو كتابة أوامر يومية.

## 10. الأصول والأنيميشن

- رفع ومعاينة وفحص نوع وحجم وأبعاد الملفات.
- فحص Sprite Sheet حسب أبعاد الصورة الفعلية وعدد الإطارات المحدد، لا افتراض مقاس ثابت.
- محرر قص ومعاينة الإطارات قبل اعتمادها.
- استبدال الأصل مع الاحتفاظ بإمكانية الرجوع.
- كشف الأصول غير المستخدمة والمرتبطة.
- الحفاظ على الأصول والأنيميشنات المعتمدة دون تغيير غير مطلوب.

## 11. الاختبار

لكل نوع محتوى:
- اختبار منفرد.
- اختبار تفاعل مع العناصر المرتبطة.
- اختبار ضمن مرحلة كاملة عند الحاجة.
- تسجيل النتائج والأخطاء.
- عدم نشر التعديل إذا فشل اختبار إلزامي.

يجب الفصل بين الاختبارات الآلية والتحقق الفعلي داخل المتصفح/الجهاز. لا يُدّعى نجاح أي اختبار لم يُنفذ.

## 12. الأمان

- جلسات وصلاحيات واضحة.
- حماية عمليات النشر والحذف والاسترجاع.
- سجل تدقيق.
- عدم كشف الأسرار في الواجهة أو المستودع.
- التحقق من الملفات والمدخلات.
- منع تعارض التعديلات المتزامنة.
- فصل محتوى اللعبة عن بيانات حسابات اللاعبين وتقدمهم.

## 13. قواعد التطوير والتسليم

1. لا واجهة دون API وبيانات وتشغيل فعلي.
2. لا تكرار لمصدر القيمة الواحدة.
3. لا نقل جماعي أو إعادة كتابة كبيرة دون حاجة مثبتة.
4. لا تغيير للأصول المعتمدة دون طلب أو دليل.
5. لا دمج إلى `main` دون موافقة صريحة.
6. لا خدمات مدفوعة دون موافقة مسبقة.
7. لا Terminal للعمليات اليومية التي يجب أن يوفرها Studio.
8. كل مرحلة لها معايير قبول واختبارات وتوثيق.
9. لا يبدأ العمل في مرحلة لاحقة قبل اجتياز بوابة المرحلة الحالية.
10. تُسجل القيود والنتائج الفعلية بشفافية.

## 14. قاعدة القرار النهائية

أي ميزة جديدة لا تُعد مكتملة إلا عندما يستطيع المستخدم إدارتها من Studio بسهولة، وإنشاء محتواها وتعديله واختباره ونشره وإيقافه واسترجاعه، ويكون ذلك متصلًا فعليًا ببيانات اللعبة ومحركها.

**لا نُقيّد Studio بحدود الكود الحالي؛ نطوّر البنية والمحرك عند الحاجة لتحقيق الميثاق، مع الحفاظ على السلوك والأصول المعتمدة.**


## 15. توسعة القدرات والاستعداد للمستقبل
- لا تُحصر أنواع المحتوى أو القدرات في قائمة مغلقة تعيق توسعة اللعبة.
- Capability غير مدعومة تتطلب مسار تطوير للمحرك، API/contract، Studio UI، sandbox tests، ثم اعتماد؛ لا إعدادات وهمية.
- إطار تفاعلات موحد يحدد الأولويات والحالات والتعارضات والتسجيل.
- فصل بيانات اللعبة عن اللاعب والحفظ، مع migrations والتوافق ومنع تكرار العمليات الحساسة.
- الاستعداد لمنصات ومحتوى اجتماعي/جماعي دون تنفيذ Multiplayer مبكرًا.
- Localization/RTL وAccessibility تُصمم كقدرات قابلة للتوسع وتنفذ تدريجيًا.
- المساعد المحادثي يقدم مقترحات ومسودات وتقارير واختبارات، ولا ينشر تلقائيًا أو يدعي تحققًا غير منفذ.
- مراقبة المحتوى، incident، disable وrollback جزء من تصميم التشغيل.


### 10.1 Auto-Rig وHybrid/Skeletal Rig ضمن دورة الأصول الموحدة

Auto-Rig وHybrid/Skeletal Rig قدرات داخل **Asset & Animation Studio** وليسا مشروعين مستقلين أو نظامي تخزين/نشر منفصلين.

- Auto-Rig ينتج مقترحاً قابلاً للمراجعة، ولا يعتمد Rig تلقائياً أو يتجاوز موافقة المستخدم.
- Hybrid/Skeletal Rig نمط تحريك اختياري للأصل إلى جانب Sprite Sheet، ويُحفظ داخل سجل الأصل نفسه.
- الأجزاء والعظام وAttachments وHitboxes ترتبط بمعرفات أصول ثابتة، وتدخل في فاحص التبعيات.
- كل تعديل ينشئ مسودة/Revision، ويخضع للتحقق والجاهزية والاختبار.
- نشر Rig يجب أن يتضمن كل ملفات الأجزاء والمراجع والكتالوج في حزمة إصدار واحدة.
- التفعيل يمر بمسار المراجعة والنشر الموحد، ويظل الإصدار السابق قابلاً للاستعادة.
- لا يُعد Auto-Rig أو Hybrid Rig مكتملاً دون إثبات المعاينة الفعلية داخل Phaser والاختبار في سياق اللعب، وليس مجرد نجاح المحرر أو المقيّم الحسابي.
